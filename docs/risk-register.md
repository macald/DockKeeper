| R-013 | N | **The `dockkeeper://` control surface is unauthenticated.** Any local process that can open a URL can `unlock` or `pause` DockKeeper with no prompt (DK-FR-010). | R-008 | K | **Accessibility behavior changes between macOS releases.** Reopened 2026-09-02. The old reopen trigger ("if a follow-focused-window feature ships") could never fire, because neither AX feature is a follow-window feature: the risk was closed behind a condition that does not describe it. | Medium | Medium | Both consumers are opt-in and both fail **open** — a revoked or never-granted permission degrades each to a silent no-op with a caption, never to a broken app. Per-macOS-release verification rides the [release checklist](release-checklist.md) alongside the CoreDock smoke test. TCC and event-tap semantics are the specific surfaces to re-check. | Open — reopened 2026-09-02 (was wrongly closed 2026-07-22) |
| R-015 | N | **The bottom-Dock guard's event tap is a continuous-cost, system-wide mechanism whose end-to-end effect is unobserved.** DK-FR-014 installs a `CGEventTap` in modify mode over mouse-move and drag events; while armed, every pointer movement on the machine crosses DockKeeper's callback on the **main run loop**. Two things follow. (1) DK-NFR-001's "~0% idle CPU" budget has never been measured, and this is the first mechanism in the app with a per-event cost. (2) ~~That the clamp stops a *real hand* completing the summon is **INFERRED**~~ — **CONFIRMED on-device with a control 2026-09-02** ([hardware matrix session 3](hardware-matrix-results.md)); this half of the risk is retired. | Medium | Medium | Off by default and opt-in, so no user carries the cost unasked. Fails **open** in every degraded state (no grant, refused tap, revoked grant, system-disabled tap), and the tap is process-owned — no persisted state, no launch repair, quit by any route releases the pointer. The pointer-level confirmation is **done** (2026-09-02). Measurement remains an M6/DK-NFR-001 gate and is the **whole of what is left here**: spot samples were incoherent, and a synthetic `CGEvent.post` load reads ~25x high, so only the 24 h soak settles it. macOS never disabled the tap for slowness across the session, which is a positive signal on the callback's latency but says nothing about aggregate cost. | Open — new 2026-09-02 (ADR-015 / #60) |
| R-012 | N | **Coexistence with an installed DockLock fights corrections.** Migrating users (the target audience of a replacement) will have DockLock installed, possibly running, during the switch — two agents correcting the Dock is the textbook oscillation scenario. Observed 2026-07-23: the dev rig itself has DockLock Lite installed (not running). Updated 2026-08-17 (ADR-012 investigation): `/Applications/DockLock Lite.app` is now **absent** (CONFIRMED — `ls`), but `pro.docklock.lite` remains an **enabled** login item in both BTM (`sfltool dumpbtm`) and System Events — an orphaned autostart entry for a deleted competitor, and the unrefuted alternative explanation for one of the two Dock-managing menu-bar icons that prompted DK-FR-012. Uninstalling the competitor evidently does not clear its login item, which sharpens this risk for migrating users. | Medium | Medium | Oscillation guard already ships (6/60 s → `Error` + explain); PROPOSED: detect a running DockLock process and show a friendly "quit DockLock while DockKeeper is enabled" note; README migration section — which should now also tell migrators to check **System Settings → General → Login Items** for a stale DockLock entry. | Open — new 2026-07-23, evidence added 2026-08-17 |

| R-016 | N | **The published live record is a belief, and a stalled publisher publishes a confident stale one.** DK-FR-015 lets any process read what the running instance holds, and liveness is decided against the kernel process table — never against a clock, because a freshness threshold needs a tolerance and a tolerance is a guess (ADR-016). Refusing that guess is right, and it is exactly what creates this risk: an instance that is wedged, or whose publish path stops being reached, is still *provably alive*, so its last record classifies `.live` and its frozen state is presented as current. Two lags are structural rather than accidental. `publishLiveGuardState()` runs from the tail of `applyBottomDockGuard()` and **never** on the tap callback — an encoder and a defaults write on the mouse-move path is what macOS disables a tap for — so `clampCount`/`reenableCount` refresh at the poll cadence (`max(5, recoveryInterval)`, 30 s by default), and `systemEnabled` is a snapshot of `CGEvent.tapIsEnabled` taken at publish time rather than a live reading. An instrument built to end confident wrong answers is the worst place in the app to have one. | Low | Medium | **Staleness is made visible rather than prevented**, which is the only honest option once the clock is refused as evidence. Two stamps travel and every reader renders both as ages: `observedAt` ("how fresh is this reading") and `stateChangedAt` ("how long has it been like this"), kept apart so a counter-only write cannot refresh the change stamp — folded together, the second question becomes unanswerable the moment the guard starts clamping. `TapRecord` is **optional**, so a released tap's stale totals are unreachable at compile time rather than by convention (the counters reset in `start()` and never in `stop()`), and `armedAt` rides inside it so a count can never be printed without the window it was counted over. `systemEnabled` separates "armed" from "actually filtering" — a state nothing in the codebase could observe before. `LiveGuardRecord`'s own docstring states the belief limit, and `--diagnostics` names which side acts when the two disagree. **Residual:** nothing flags a record that *should* have been rewritten by now, because that check is the freshness threshold the classifier deliberately refuses; a reader who ignores the age they are shown still gets a stale answer. The reader half is **CONFIRMED on-device 2026-09-03** (real `com.dockkeeper.app` domain, real kernel — a `kill -9` was classified `writerGone` on a **19-second-old** record, which a freshness design would have called live); the app's own publish and retract wiring is **CONFIRMED on-device 2026-09-04** ([session 6](hardware-matrix-results.md), closing [#96](https://github.com/blamechris/DockKeeper/issues/96)) — publish on a real state change with a 20 s idle control, retraction on a clean quit, and the armed heartbeat measured at four consecutive 30 s refreshes. The **Residual above is unchanged and was demonstrated in the same sitting**: [#87](https://github.com/blamechris/DockKeeper/issues/87) reproduced on device as a log line reading `armed over 1 span(s)` for a tap the live record showed holding **2** — one arm event, two instruments, and the stale one is the one that existed before this feature. | Open — accepted, new 2026-09-03 (ADR-016 / DK-FR-015 / #78) |
| R-014 | N | **The cross-launch repair restores an auto-hide the user set themselves.** DK-FR-013 turns Dock auto-hide back off at launch when a hide record survives a killed process and auto-hide currently reads on. That reading is genuinely ambiguous: "nothing touched it since we died" is **not separable** from "the user turned it off and then deliberately on", "the user saw it on and decided they like it", or "a third party (a script, DockLock Lite) set it" — no intent signal exists, and the exposure window opens when the process *died*, which is unobservable from the next launch (ADR-013, Consequences). | Low | Low | The repair **never writes without first observing auto-hide ON** (a 48-combination unit sweep asserts it), so an already-off Dock is discharged with zero Dock writes; a **7-day attribution window** retires the claim by acquiescence — a setting lived with that long is the user's, whoever wrote it; a live capture is **adopted**, not un-hidden, so the Dock cannot flash mid-share; and the change is **announced in the menu** on both acting branches (`.adopt`'s disclosure is deferred to the restore that discharges it, not dropped), reversible in one checkbox, fires at most once per crash, and self-clears. The cost asymmetry is deliberate and recorded: a false restore is visible in seconds and reversible; a false non-restore is the issue #29 bug — an unexplained auto-hiding Dock with no in-app recovery. | Open — accepted, new 2026-08-17 (issue #29 / ADR-013) |

| ID | Lineage | Risk | Outcome |
|---|---|---|---|
| R-001 | K | **No supported API can reliably move the Dock** (was: High/Critical — the project's founding uncertainty). | **Retired 2026-07-22 for edge lock**: the feasibility spike CONFIRMED on-device that `CoreDock` sets the edge live and flicker-free, with `defaults`+`killall` as a public-path fallback. The *display* dimension of the risk lives on as R-002 (no direct API exists; main-display relocation is the accepted best-effort route, owner Decision 1). |
| R-007 | K | **App Sandbox blocks required behavior.** | **Materialized and accepted 2026-07-22**: the sandbox blocks both `killall` and private-API use (CONFIRMED policy), so Mac App Store distribution is off the table for v1. | R-010 | K | **"DockKeeper" may conflict with an existing product name or trademark** (competitor family: DockLock). | **Closed 2026-07-24 — reviewed and cleared** (owner-delegated). Research findings: no "DockKeeper"/"Dock Keeper" product, app, or USPTO filing exists (web + marketplace + USPTO searches, 2026-07-24); the only DOCKLOCK registration ever (79142224) was for offshore mooring systems and was **cancelled 2016**; DockLock-the-software shows no registered mark. "Dock" is descriptive for the category; DockKeeper shares no distinctive element with DockLock; DockKeeper is free/MIT (no sales confusion motive). Residual risk assessed low; revisit only if a filing appears. |
| R-011 | N | **A live CoreDock set may not survive a Dock restart.** | **Closed 2026-07-22**: on-device spike CONFIRMED `CoreDockSet` writes through to `com.apple.dock` defaults ([findings](spikes/coredock-defaults-persistence.md)) — restarts re-read the edge we set. No mirroring, no Dock-restart detection needed; the release-checklist CoreDock smoke test re-verifies per macOS release. |

## Review cadence

Re-review at each milestone boundary ([implementation plan](implementation-plan.md)) and at every macOS point release while R-004 is open. Additions require an ID, lineage, likelihood/impact, and a named mitigation; closures record the evidence (kickoff rule 15: record risks instead of silently assuming them away).
